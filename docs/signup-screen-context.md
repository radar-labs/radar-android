# Context: "Sign up" registration screen (Figma → Android)

Handoff doc so another chat can continue this work. Branch: `mapping-ios-commits`.

## Goal

Implement the Figma **"Sign up"** screen and reach it from the existing welcome screen.

- Figma node: https://www.figma.com/design/EuVfFGTZk49fHRff0HxeLp/Radar?node-id=425-2616
- Design contents: a blue **person icon**, title **"Sign up"**, two-paragraph body
  (`Create a new account or restore an existing Signal account` + `Radar is based on Signal and
  compatible with it, letting you keep all your existing conversations`, with **"Radar is based on
  Signal"** highlighted in blue), a filled blue **Create New Account** button, and a blue
  **Use my Signal account** text link.

## Where this lives in the app

Registration is a classic **Android Views/XML + Navigation Component** flow (not Compose) hosted by:

- `app/.../registration/ui/RegistrationActivity.kt`
- Nav graph: `app/src/main/res/navigation/registration_v3.xml` (id `@+id/signup`, start = `welcomeFragment`)

The first screen is `WelcomeFragment` (Radar-logo welcome with **"I'm new to Radar"** /
**"I already have an account"** buttons). There was also an **unused** parallel Compose
registration flow in the standalone `registration/lib` module (`RegistrationNavHost` +
`screens/welcome/WelcomeScreen.kt`, etc.) — see "Open item" below.

## Flow implemented

```
WelcomeFragment
  ├─ "I'm new to Radar"          → SignUpFragment   (NEW — the Figma screen)
  └─ "I already have an account" → RestoreWelcomeBottomSheet (unchanged)

SignUpFragment ("Sign up")
  ├─ "Create New Account"   → permission check → EnterPhoneNumberFragment (create new account)
  └─ "Use my Signal account"→ RestoreWelcomeBottomSheet → restore/transfer flow
                              (RestoreViaQr / SelectManualRestoreMethod), mirrors WelcomeFragment
```

`SignUpFragment` deliberately replicates `WelcomeFragment`'s create/restore navigation logic
(permission grant via `GrantPermissionsFragment`, `RestoreWelcomeBottomSheet` result handling,
`RegistrationViewModel.maybePrefillE164 / intendToRestore / setRegistrationCheckpoint`). The
`GrantPermissionsFragment` result is delivered on the host's `parentFragmentManager` keyed by
`GrantPermissionsFragment.REQUEST_KEY`, and only the currently-resumed destination consumes it,
so Welcome and SignUp don't conflict.

## Open item — DECIDED: leave it

The user originally asked to "remove the orphaned Compose welcome screen." It is **not** a
standalone file — `registration/lib/.../screens/welcome/WelcomeScreen.kt` (+ `WelcomeScreenEvents.kt`,
test) is the start screen of an entire self-contained, app-unused Compose registration module
(`registration/lib`: its own `RegistrationActivity`, `RegistrationNavHost`/`RegistrationNavigation.kt`
referencing `RegistrationRoute.Welcome`, ~12 sibling screens, and `RegistrationNavigationTest.kt`).
Deleting just the welcome files breaks that module's compilation.

**Decision (2026-05-28): leave it for now** — nothing was removed. The Compose registration module
is untouched. Revisit cleanup separately if desired (options were: remove the whole unused Compose
flow, or delete only the welcome files + patch `RegistrationNavigation.kt`/its test to keep
compiling).
